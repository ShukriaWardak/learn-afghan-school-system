# Sample AFN Finance ledger

This development increment adds a provisional income/expense cashbook to the authenticated branch-approval stack, the latest reference dashboard and graduation photo, and the navigation fixes from PR 15. It does not implement payroll, budgets, bank reconciliation, financial approvals, deletion, or a double-entry accounting system. The Finance page uses the dashboard's light palette; the existing sign-in and role-specific navigation are retained.

## Fields

Each record has a date, income/expense type, category, positive AFN amount, branch or central office, payer/payee, payment method, optional receipt/voucher reference, description and optional notes. An edit also needs a correction reason. Reference numbers, creator, editor, timestamps and versions are generated by the server. Categories are sample choices that can be finalized with the team.

Amounts are decimal strings end to end and use `DECIMAL(14,2)` in MySQL/MariaDB. Display and totals avoid floating-point conversion. Totals cover every matching record, while the table uses pages of 50. Income minus expenses excludes opening balances and is not a verified cash/bank balance.

## Access

| Account | Read | Add/edit | Delete |
| --- | --- | --- | --- |
| Active `department_user` in a department whose code is `FINANCE` | Assigned finance area | Assigned finance area | No |
| Super administrator | All Finance entries | No | No |
| Other department, zone and branch roles | No | No | No |

Finance accounts with no zone/branch assignment can work with central-office and branch entries. Existing zone/branch assignments narrow records, branch choices, totals and writes; when both assignments exist both must match. Central-office entries are excluded for scoped accounts. Accounts without an available assigned office cannot add records. Membership and active status are checked in MySQL on each request. The five-person team is a planned staffing count, not an automatic account-creation rule or hard-coded user list. No real accounts are created by this update.

## Install on a development copy

1. Use this feature's complete source so `finance.js` and the updated PHP/frontend entry points are installed together. Keep your own ignored `backend/config.local.php`.
2. Inspect `check-setup.php` and the existing schema. Obtain the database owner's approval before applying a migration to a populated installation. On a fresh disposable database, apply `schema.sql`, then migrations 002 through 007 in order. Migration 007 creates `finance_entries` and seeds no accounts or transaction data. `CREATE TABLE IF NOT EXISTS` does not repair an incompatible existing table.
3. Use an owner-provisioned active Finance account with role `department_user` and department code `FINANCE`. Provisioning real users and assigning their scopes is a separate authorized task. Do not run the test fixture scripts on a working school database.
4. Start Apache/MySQL and open your project's `index.html` through localhost. Finance members land on Finance; super administrators can open Finance from the sidebar in read-only mode.
5. With synthetic data, add an income and expense, reload, filter by date/type/office/search and verify totals. Edit with a correction reason, then check the latest value from a second Finance session. Verify that a stale form keeps the typed values and asks for a refresh.
6. Verify super-admin read-only behavior, branch/zone boundaries, denied roles and immediate clearing of dialogs/records after session expiry. Confirm the existing login and other modules on the team's actual XAMPP installations.

## Integrity and limits

Creates use a submission UUID: retrying the same payload by the same user returns the saved ID without inserting again; conflicting reuse is rejected. Corrections use optimistic versions plus row locking. Each write and its audit event commit together or roll back together. This prevents duplicate retries, not independently entered duplicate receipts with different submission UUIDs. No delete endpoint or financial approval policy is introduced.

The sample supports the five planned team members without seeding their names or passwords. It does not provide a Finance user-management screen, salary calculations, attachment uploads, CSV/PDF finance exports, or live database synchronization between teammates. Test code uses synthetic fixtures only. Local XAMPP acceptance and final field/permission review remain necessary before real records are used.
